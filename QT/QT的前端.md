## QT项目的构建

使用QT编写的程序本质上是C++程序，因此除了显式的c++文件外，那些QT特有的文件类型，.qrc和.ui，都会被编译成c++文件，这样才能集成于项目中



### .ui文件

[name].ui文件会被qt的用户界面编译器（uic，User Interface Compiler ）编译成一个对应的ui_[name].h文件集成到项目里面

所以，如果你想使用一个.ui文件，唯一的方式就是#include ui_[name].h

ui文件会自动生成一个setupUI函数，里面就是把控件一个个的实例化，设置信息然后作为你的窗口类的子类

然后调用QMetaObject::connectSlotsByName自动把你定义的槽函数与对应的控件信号连接

使用ui跳转到槽的时候，qt会寻找这个ui文件绑定的类名，然后在这个类下面定义槽



## QT GUI的工作原理

### 怎么显示

首先，所有 GUI 显示的最终都是生成像素点写入显存，然后显示器会读取显存并按某种频率刷新显示器

那么问题就是，谁来计算这些像素点？CPU不会干这件事情，生成像素点是数据密集型任务，可以并行的，CPU只适合处理任务密集型，会由专门的处理并行计算的显卡来计算

那么显卡又是怎么计算的？答案是显卡接收专门的指令集编写的指令然后计算

那么这些显卡指令又是怎么来的？答案是需要有专门的程序来生成，这些程序接收更高级别的抽象，生成显卡看得懂的指令，如 NVIDIA 的 CUDA 指令、AMD 的 GCN 指令

这些程序就是显卡驱动程序，这些程序提供的抽象就是通用图形API规范如DirectX，Vulkan，OpenGL

显卡驱动会把这些API规范先翻译为中间指令格式，如DirectX API -> DXIL,Vulkan -> SPIR-V,OpenGL -> SPIR-V/GLSL

然后再把这些中间指令格式翻译为自家硬件指令如NVIDIA → PTX/SM, AMD → GCN

终于到了这个地方了，游戏引擎如UE5，Unity，GUI开发框架如QT，WPF，浏览器渲染引擎如Chrome的Blink、Firefox的Gecko，都是对图形API的封装，最后成为这些开发环境使用的编程接口

也不是说像素点生来就是被GPU计算的，对于小型任务，CPU其实也可以干这个活，那么这个图形API就叫GDI

当然，作为用户程序是不可能有权限直接操作显存的，只能通过图形API，这是由操作系统强制规定的

操作系统提供图形管理和窗口API，用户程序需要创建窗口获取资源，然后在把对应的资源传入图形API中

### 怎么交互

好了，显示的原理讲清楚了，那么，交互呢？这些应用程序是如何响应你的操作的？

我们知道，响应IO的方式有轮询，阻塞I/O（立即阻塞），异步I/O（选择时机主动阻塞），假设我们的程序模型是单线程的。

QT程序在不使用多线程的情况下都是单线程模型，这意味着，如果你写一个死循环并在某个时候执行，那么鼠标点击按钮，键盘输入是会卡住的。

那么，QT程序选择什么模型来响应鼠标和键盘呢？答案是基于异步I/O的事件驱动，这很好理解，几乎所有图形化交互应用程序都是这样干的。

键盘和鼠标的交互信息会先通过驱动捕获并送入操作系统的全局消息队列，然后操作系统会唤醒QT应用，QT应用获取消息加入事件队列然后执行。
