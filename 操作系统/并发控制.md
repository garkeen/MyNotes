### 原语

什么是原语？

假如给num加1，需要三个汇编指令

get num; //p1

num++; //p2

load num; //p3

显然，这个过程可以在p1 p2处被打断，然后切换到另一个进程，此时如果另一个进程执行与num有关的操作，那么可能出现

脏读：读取了正在处理的数据

写丢失：本来处理好的结果被覆盖

类似的问题有很多，很多时候我们希望某种事情可以原子的完成，不过这个原子的完成到底是什么意思？

可以是真正意义上的原子完成，也就是完成这个任务在时间上是连续的，无法被中断；

可以不是真正意义上的原子完成，而是限制其他进程与这个原子任务数据进行任何读写操作；

那么为了解决这个问题，我们有三种办法

一就是关中断，禁止给num加1途中切换进程（太危险）

二就是设置互斥区，其他进程需要提前检测数据是否在使用

三就是设置原子指令，使得一个汇编指令可以同时完成给num加1的操作（对于复杂事件显然不可取）

很显然，锁无法实现关中断的效果，因为其他进程只会在与锁有关的逻辑下阻塞，而关中断其他进程可以在任何逻辑下被阻塞

比如两个进程都在干一件事：

| 进程1     | 进程2     |
| --------- | --------- |
| A；       | B;        |
| C;        | D;        |
| get num;  | get num;  |
| num++;    | num++;    |
| load num; | load num; |
| E;        | F;        |

对于进程A，如果在与num有关操作下开中断，那么进程B（假设处在B阶段）一直都会卡在B阶段；

而如果只是使用锁，那么进程B（假设处在B阶段）不会一直都会卡在B阶段，而是一直到临界区（D之后）才会被阻塞。

### 锁

我们只讨论如何实现锁，锁提供了以下保障：

任何时间只有一个进程可以获得锁；

只有获得锁的进程才可以进入临界区；

锁可以用硬件原语（TAS,SWAP）加判断实现任意时刻只有一个进程获得锁；

也可以使用软件实现。不过这里就需要严格证明你的逻辑是正确的，比如peterson锁，bakery锁

那么如果没有获得锁怎么办？答案是要么循环获取，也就是自旋，但是自旋太浪费CPU了，因此可以先把自己阻塞起来，等有人开始放锁的时候再去抢锁（注意，就算有人放锁然后把自己唤醒，并不意味着自己已经得到锁了，还是得重新抢）

自旋锁

```
lock(&m)

{

while(tas(&m,1)==1){};

//那么这个while最少 或者期望会等待多久？答案是一个进程的完整的lock run unlock时间 其中的run是用户自定义行为 可以任意长

}

unlock(&m)

{

tas(&m,0)

}
```

阻塞锁

```
lock(&m)

{

while(tas(&m,1)==1){

sleep self into m-queue;

};

}

unlock(&m)

{

tas(&m,0)

wakeup one proc in the m-queue;

}
```

抛开效率不谈（上下文切换，调度），两者的行为完全一致，

### 条件变量

本质上其实是一个条件判断的锁+阻塞队列

为什么需要锁？因为需要原子性的判断+等待

如果某进程A判断发现条件不满足，但是在等待执行之前发生进程切换，切换到进程B，而进程B恰好运行到使得这个条件满足，之后B错误的释放了满足的信号（此时不会唤醒任何线程），而进程A则会永远陷入睡眠不会被唤醒（丢失唤醒）

为什么睡眠需要释放锁？因为如果你不释放，其他人都在等待条件判断锁，而只有你能释放，但是你又睡眠了，导致死锁

Mesa语义

为什么是while不是if？因为你被唤醒不意味着条件满足，为什么？因为可能同时多个进程被唤醒，而这些进程拿到锁之后完成工作又释放锁，此时由于你被唤醒，不知道会不会出现其他进程是否也被唤醒了而且把工作做了导致条件还是不满足（唤醒竞争）

由于你要重新判断，所以你还是需要重新获得锁

```
wait(&m)

{

unlock(&m);

sleep self into a queue;

lock(&m);

这里就非常难绷，因为unlock和sleep必须一次实现，但是这里显然没有，就算在外面加锁也不行，因为自己被阻塞了无法解锁

因此必须系统提供帮助，要么

1.提供一个解锁+阻塞自己的原语

2.提供一个可以阻塞其他进程的原语，让其他进程完成阻塞自己和解锁的原子实现

显然第一个最简单，但这是提醒我们，如果操作系统只提供阻塞自己的原语，那么我们永远无法锁实现条件变量

}

signal(&m)

{

wake a proc from a queue

}

broadcast(&m)

{

wake all proc from a queue

}
```



```
use:

lock(&m)

while(!condition)

{

wait(&m);

}



free:

unlock(&m);

signal(&m);	or	broadcast(&m)
```

Hoare语义

不需要while，也不需要重新获得锁，但是实际中你很难保证你的锁可以正确交接到那个wakeup的进程，万一此时有别的进程呢？

需要对阻塞队列的顺序（一定是释放最早阻塞的进程）和调度算法（下一个调度的一定是那个被阻塞的进程）有很强的假设，而mesa语义不需要这个假设

至于唤醒，假如你是使得条件可以满足的进程，你的工作可以使得100个被阻塞的进程都可以继续运行，那么你的唤醒就需要权衡，你到底是唤醒一个还是所有？如果是一个，其他脚手架个永远被阻塞，如果是所有，但是如果你的工作只能使得一个进程可以继续运行怎么办？这说明我们唤醒的API不能只有一个，而是提供两个

pthread_cond_signal

pthread_cond_broadcast

其中选择pthread_cond_broadcast是绝对正确的，不过会浪费；选择pthread_cond_signal要注意你到底会不会使得多个阻塞进程都可以继续运行



我们知道，条件变量本质上和死循环原子的判断条件是否满足是完全一样的行为，也就是说，其实你完全可以把条件变量看成在死循环，也就是说：

```

while(!condition)

{

wait(&m);

}
```

本质上就是

```
while(true)

{

lock(&m);

if(condition){break;}

unlock(&m);

}
```

### 信号量

信号量可以看作是锁的推广，它把锁看成了某种资源

整型信号量/记录型信号量

维护一个值，并提供PV原语操作（分别是原子性的+1和-1）并判断

#### P的实现

一种实现方法是

原子性判断是否大于0，是的话减一并意味着获得资源，不是的话循环判断(**整型信号量**)

或者

原子性的-1再判断是否大于等于0，是的话意味着获得资源，不是的话阻塞自己(**记录型信号量**)

```
lock(&m)

while(value==0)

{

unlock(&m)

lock(&m)

}

value--

unlock(&m)
```

当然你可以用是否开关中断取代lock和unlock

or

```
lock(&m)

value--

while(value<0)

{

sleep self into queue and unlock(&m)

}
```



#### V的实现

原子性的+1并唤醒一个被阻塞的进程

value++

wakeup a proc from queue

对于**整型信号量**，如果value=1，那么就相当于**二进制信号量**；

对于**记录型信号量**，如果value=1，那么就相当于一个**互斥型信号量**；如果value>1，那就是**计数型信号量**.

并发约束：

互斥->每次只有一个进程可以获得锁（进入临界区）

lockA与lockA之间是互斥的 或者说 执行顺序不可能连续的越过P 比如AB进程同时完成了lockA

同步->进程C必须在AB完成后才行这本质上意味着

1.进程C和AB是互斥的（显然）

2.互斥的基础上有先后（也就是ABC才行 BAC不行）

这就相当于unlockA与lockA之间是先后的



### 关键行为澄清

互斥不意味着自始至终只有一个人能进入临界区，相反一定要保证所有想要去临界区的进程一定都能去临界区，只不过顺序不同；因此，下一次你看到两个进程在wait同一个锁，不要想着A成功B不成功，而是B**最终一定也会成功**，只不过顺序不一样

这意味拿到锁后必须有一个人释放锁！一定需要注意，不是说我拿到锁，做完临界区的事情就去干其他的了，**必须释放锁**！但是这个释放锁的人不一定是自己，不过无论怎么样，一定有一个释放同一个锁的过程，否则所有进程将会卡死无法终结

第二就是，阻塞锁释放必须额外解放一个需要这个锁的进程，这样才能完成语义功能上一致的效果，否则进程一直在阻塞队列，就算锁被释放了，自己也拿不到

并且，只要保证释放就解放一个需要这个锁的进程，那么任何阻塞锁的行为和自旋锁的行为都是一样的！也就是说抛开实现细节不谈，你**完全可以认为阻塞队列的所有进程都没有被阻塞**，而是一直再运行和自旋，等待锁的解放，这就是为什么说语义不一样，但是**行为和功能是完全一样的**，这样你就不需要担心阻塞锁会出现进程一直阻塞的错误情况



当我们没有锁的时候，我们不需要考虑两个进程会不会最终在某个循环卡住，最终无法走到结束（因为我们要求一般的进程，或者说单独一个进程最终可以顺利的完成所有工作，也就是走完一生，也就是在有锁这个概念之前，是不可能卡住的），但是我们要考虑因为临界区导致的脏读和写丢失问题

当我们有锁的时候，我们不需要考虑脏读和写丢失了（因为有锁保证），但我们要考虑更严重的问题：如何保证你写的代码运行不会出现死锁？这就严格要求了锁获取和释放的时机要正确，而且锁的顺序也要正确

所有的死锁都发生于两个或多个锁之间不对称的获取，或者说，死锁只可能发生于你连续获得两把及以上的锁，如果你只使用一把，那么只要你最后把锁放了，就没问题

我们回头看看并发各种控制，永远记住：理论上对于所有并发错误，严格的串行（也就是先完成一个进程的所有任务 再完成可以解决所有问题，但是低效率又警示我们需要适当的并行

### 同步原语的能力

显然可以用互斥锁+条件变量实现信号量，那么反过来呢？能否用信号量实现锁和条件变量？锁肯定是可以的，关键是条件变量，我们需要用信号量实现

其中主要的难点就是条件变量是无条件阻塞的，而信号量必须进行减法后value<0才会阻塞，释放倒是差不多

我们先尝试使用一个初始值为0的信号量就可以实现wait 和 signal

```csharp
class CV {
    Semaphore s = new Semaphore(0);
    Lock m;

    public void Wait() {
        m.Release();
        s.P();
        m.Acquire();
    }

    public void Signal() {
        s.V();
    }
}
```

事实上，wait的实现没有错误，虽然看起来Release()和P()不是原子的实现，但是如果在中间如果V了一下，由于进行P操作不会等待，因此这和先P后V使得wait跳出P一样

关键在于signal，如果当前队列是空的，条件变量的signal不会像V一样，预先存储一个位置（相当于value=1），如果此时有人V就不会等待，事实上，条件变量在队列是空的情况下signal不会发生任何事情，而你如果用V实现则会出bug

比如考虑下面的代码
```csharp
// 共享资源
Lock mutex = new Lock();
CV notEmpty = new CV(mutex); // 使用第一版有缺陷的实现
CV notFull = new CV(mutex);  // 使用第一版有缺陷的实现
int buffer = 0; // 0 表示空, 1 表示满
int itemCount = 0;

// 生产者线程
void Producer() {
    mutex.Acquire();
    while (itemCount == 1) { // 如果缓冲区满了
        notFull.Wait();      // 等待“不满”的信号
    }
    // 生产...
    buffer = 1;
    itemCount = 1;
    notEmpty.Signal();       // 通知消费者“不空”了
    mutex.Release();
}

// 消费者线程
void Consumer() {
    mutex.Acquire();
    while (itemCount == 0) { // 如果缓冲区是空的
        notEmpty.Wait();     // 等待“不空”的信号
    }
    // 消费...
    buffer = 0;
    itemCount = 0;
    notFull.Signal();        // 通知生产者“不满”了
    mutex.Release();
}
```
考虑一开始就完成Producer的任务，由于Signal了一下，后面执行两次Consumer()中，第二次到itemCount == 0时候，执行notEmpty.Wait()不会被阻塞，只有第三次会被阻塞，如果你此时while变成if，那么就会发生灾难

因此，如果你需要保证条件变量的signal在空队列的情况下语义是什么都不用做，那么这个实现就是错误的，因此我们需要某个数字来存储当前被阻塞的线程数，只有真的阻塞了进程再V.

```csharp
class CV {
    Mutex m;
    Semaphore s, x;
    int waiters = 0;
    public void Wait() {
        x.P(); waiters++; x.V();
        m.Release();
        s.P();
        m.Acquire();
    }
    public void Signal() {
        x.P();
        if (waiters > 0) { waiters--; s.V(); }
        x.V();
    }
    public void Broadcast() {
        x.P();
        while (waiters > 0) { waiters--; s.V(); }
        x.V();
    }
}
```

但问题是需要保证broadcast,因为假设我阻塞了100个进程，然后我一次性生产100个产品，理论上应该用broadcast才能完全实现，

如果我是基于上述的实现，那么如何实现broadcast？

如果我们基于二进制信号量，那么V两次没意义（1+1=1），无法唤醒更多线程；

如果我们基于计数型信号量，那么如果在其中有新的进程P了一下，就会丢失；

broacast的语义是释放当前被阻塞的所有线程，之后被阻塞的不管，而这个实现不能保证在Broadcast()释放x锁之前激活所有线程，如果

Broadcast()释放x锁，然后还没轮到被阻塞的线程，然后新加了一个被阻塞线程，就会出bug了

为了保证Broadcast()释放x锁前完成所有线程，需要wait完成P后给一个同步信号告诉broadcast，这就是所谓的握手机制

```csharp
public void Broadcast() {
    x.P();
    for (int i = 0; i < waiters; i++) s.V();  // 发送信号
    while (waiters > 0) { 
        waiters--; 
        h.P();  // 等待每个线程确认收到信号
    }
    x.V();  // 只有所有目标线程都确认后，才释放x锁
}

public void Wait() {
    x.P(); waiters++; x.V();
    m.Release();
    s.P();    // 被唤醒
    h.V();    // 确认收到信号
    m.Acquire();
}
```

### PV无法做到的问题

在纯粹使用PV而且不使用循环（也就是忙等待）的情况下，假设不能使用信号量数组，那么以下问题无法解决

顾客无阻塞的拿一个全局递增的号并等待叫号，厨师做好菜并把菜给当前持有号最小的等待的那个顾客

这是不可能的，因为多个顾客等待的情况下，厨师的V无法保证是最小的顾客拿到（不对阻塞队列做假设），因此必须用while

关键在于，如果不允许拿号中阻塞，那么无法区分等待后被唤醒到底是谁，如果允许的话，让第一个拿到锁不放，那么自然就可以了，接下来的人只有拿到锁才可以++
